# WPFでクリップボードへのコピー処理中にプログレスバーを動かすには？
* 10000x10000ピクセルの画像をコピーしていて完了まで数秒かかる
* プログレスバーは進捗率ではなくて動いているのが分かれば良い「IsIndeterminate="True"」
* プログレスバーのIsIndeterminateは処理開始前は"false"、処理中は"true"

以下のコードではプログレスバーが停止したまま処理が終わってしまう

```cs
        private async void CopyTest()
        {
            if (MyBitmapSource is null) { return; }

            // 1. UIを「処理中状態」にする（この時点ではまだ画面に反映されない）
            MainContainer.IsEnabled = false;
            MyProgressBar.IsIndeterminate = true;
            
            if (MyBitmapSource.IsFrozen) { MyBitmapSource.Freeze(); }

            await Dispatcher.InvokeAsync(() => { }, DispatcherPriority.Background);

            Application.Current.Dispatcher.Invoke(() =>
                {
                    try
                    {
                        // 3. 画面が書き換わった後、クリップボードへのコピーを実行する
                        Clipboard.SetImage(MyBitmapSource);
                    }
                    catch (Exception ex)
                    {
                        MessageBox.Show($"エラーが発生しました: {ex.Message}", "エラー", MessageBoxButton.OK, MessageBoxImage.Error);
                    }
                    finally
                    {                        
                        MainContainer.IsEnabled = true;
                        MyProgressBar.IsIndeterminate = false;
                    }
                });
        }
```

<br><br><br>



WPFでプログレスバー（`IsIndeterminate="True"`）が動かない原因は、**クリップボードへのコピー処理（`Clipboard.SetImage`）をUIスレッド（メインスレッド）で実行してしまっているから**です。

現在のコードでは、`Application.Current.Dispatcher.Invoke(...)` を使って、重い処理をわざわざUIスレッドに投げ直しています。そのため、コピー中の数秒間はUIスレッドが完全にロックされ、プログレスバーのアニメーションを描画する余裕がなくなっています。

これを解決するには、**`Clipboard.SetImage` をUIスレッドとは別のスレッド（バックグラウンドスレッド）で実行する**必要があります。

---

## 解決コード（STAスレッドでのバックグラウンド処理）

WPFのクリップボード（`Clipboard`）は、**STA（Single Threaded Apartment）スレッド**からしか呼び出せないという制約があります。そのため、単純に `Task.Run` を使うだけだとエラーになります。

新しくSTAスレッドを作って、そこでコピー処理を走らせるのが一番確実です。

```csharp
private async void CopyTest()
{
    if (MyBitmapSource is null) { return; }

    // 1. UIを「処理中状態」にする（IsIndeterminateをTrueに）
    MainContainer.IsEnabled = false;
    MyProgressBar.IsIndeterminate = true;
    
    // 画像は別スレッドに渡す前に必ず Freeze する必要があります
    if (!MyBitmapSource.IsFrozen && MyBitmapSource.CanFreeze)
    {
        MyBitmapSource.Freeze();
    }

    // 2. 新しいSTAスレッドを作成して、バックグラウンドでクリップボード処理を実行
    bool isSuccess = false;
    Exception exception = null;

    await Task.Run(() =>
    {
        // STAスレッドを立てるための設定
        var thread = new System.Threading.Thread(() =>
        {
            try
            {
                // バックグラウンドのSTAスレッドでコピーを実行
                Clipboard.SetImage(MyBitmapSource);
                isSuccess = true;
            }
            catch (Exception ex)
            {
                exception = ex;
            }
        });

        thread.SetApartmentState(System.Threading.ApartmentState.STA); // 必須設定
        thread.Start();
        thread.Join(); // スレッドの完了を待つ
    });

    // 3. UIスレッドに戻ってきたので、結果の表示とUIの復元を行う
    if (!isSuccess && exception != null)
    {
        MessageBox.Show($"エラーが発生しました: {exception.Message}", "エラー", MessageBoxButton.OK, MessageBoxImage.Error);
    }

    MainContainer.IsEnabled = true;
    MyProgressBar.IsIndeterminate = false;
}

```

---

## ポイントの解説

* **`MyBitmapSource.Freeze()` の重要性**
WPFのUI要素や画像（`BitmapSource`）は、通常それを作ったUIスレッドからしかアクセスできません。しかし、`Freeze()`（凍結）を行うことでオバジェクトが変更不可（読み取り専用）になり、**別のスレッドへ安全に渡せる**ようになります。
* **なぜ `Task.Run` の中で `Thread` を作っているのか？**
`Task.Run` が使用するスレッドプールは「MTAスレッド」です。WPFのクリップボードは「STAスレッド」を要求するため、タスクの中で明示的に `SetApartmentState(ApartmentState.STA)` を指定したスレッドを起動しています。
* **UIのフリーズが解ける理由**
重いコピー処理が別スレッド（バックグラウンド）に引っ越したため、UIスレッドが完全に暇になります。これにより、プログレスバーのアニメーション（描画処理）が毎フレーム滑らかに実行されるようになります。

プログレスバーが止まったままになってしまう原因は、**「重い処理（画像の拡大縮小・エンコード・保存）」がUIスレッド（メインスレッド）上で実行されているため**です。

`BitmapToPngImageToClipboard` メソッドは `async` になっていますが、`await Task.Run(...)` に到達するまでの処理（`MakeScaleBitmap`、`pngEnc.Save(ms)` など）はすべてUIスレッドを占有して動いています。そのため、プログレスバーのアニメーションを描画する余裕がUIスレッドに残っていません。

これを修正するには、**重い処理全体を `Task.Run` を使ってバックグラウンドスレッドへ逃がす**必要があります。

---

## 改善のポイントとコード例

WPFのUI要素（`BitmapSource` など）は基本的に作成されたスレッド（UIスレッド）でしか扱えませんが、`BitmapFrame.Create(source)` で作成したフレームやエンコード処理自体は、引数の `source` がフリーズ（`Freeze()`）されていれば、バックグラウンドスレッドでも安全に扱えます。

以下のように修正すると、プログレスバーが滑らかに動くようになります。

```cs
private async void ButtonCopyToClipboardExterior_Click(object sender, RoutedEventArgs e)
{
    // 1. 最初にUIスレッド側でプログレスバーやカーソルを設定
    MyStatusText.Text = "コピー処理中";
    MyProgressBar.IsIndeterminate = true;
    Mouse.OverrideCursor = Cursors.Wait;
    MyMainGrid.IsEnabled = false; // 二重クリック防止など

    try
    {
        // 2. メモリチェックや確認（UI要素が絡むためUIスレッドで行う）
        if (!CheckMemoryAndConfirmConsent(ImageControl))
        {
            // キャンセルされた場合は元に戻す
            ResetUiState();
            return;
        }

        // 3. 元の画像データを取得し、別スレッドで扱えるようにフリーズする
        // ※MyBitmapSourceがUIスレッド依存の場合、ここでFreezeしておきます
        BitmapSource sourceToProcess = MyBitmapSource;
        if (!sourceToProcess.IsFrozen && sourceToProcess.CanFreeze)
        {
            sourceToProcess = sourceToProcess.Clone();
            sourceToProcess.Freeze();
        }

        // 現在のスケール値をローカル変数にコピー（スレッド間安全のため）
        double scale = MyImageScale;

        // 4. 重い処理（リサイズ、エンコード、クリップボード転送）を丸ごと非同期(Task.Run)で実行
        await Task.Run(() =>
        {
            // A. 画像のスケール・エンコード処理
            // ※MakeScaleBitmap内で新しいBitmapを作成する場合、
            //   そのメソッド内で新しいBitmapをFreeze()するか、スレッド依存に注意してください
            BitmapSource scaledSource = MakeScaleBitmap(sourceToProcess, scale);
            
            // バックグラウンド側で作ったBitmapも、別スレッド（STAスレッド）に渡すためにFreezeが必要
            if (!scaledSource.IsFrozen && scaledSource.CanFreeze)
            {
                scaledSource.Freeze();
            }

            PngBitmapEncoder pngEnc = new();
            pngEnc.Frames.Add(BitmapFrame.Create(scaledSource));
            
            using var ms = new System.IO.MemoryStream();
            pngEnc.Save(ms);

            // B. クリップボードへの書き込み（STAスレッドが必要）
            Thread thread = new(() =>
            {
                // MemoryStreamは position 0 から読み込める状態にする
                ms.Position = 0;
                Clipboard.SetData("PNG", ms);
            });

            thread.SetApartmentState(ApartmentState.STA);
            thread.Start();
            thread.Join(); // STAスレッドの完了を待つ
        });

        MyStatusText.Text = "コピー完了";
    }
    catch (Exception ex)
    {
        MessageBox.Show($"エラーが発生しました: {ex.Message}", "エラー", MessageBoxButton.OK, MessageBoxImage.Error);
        MyStatusText.Text = "コピー処理中にエラー発生";
    }
    finally
    {
        // 5. 成功・失敗に関わらずUIの状態を元に戻す
        ResetUiState();
    }
}

// UI状態をリセットするヘルパーメソッド
private void ResetUiState()
{
    MyMainGrid.IsEnabled = true;
    MyProgressBar.IsIndeterminate = false;
    Mouse.OverrideCursor = null;
}

```

## 修正箇所の解説

1. **プログレスバーの開始タイミング**
元のコードでは、メソッドの奥深く（`BitmapToPngImageToClipboard`）でプログレスバーを開始していましたが、イベントハンドラーの直後で開始するのが最も確実です。これにより「ボタンを押した瞬間にアニメーションが始まる」ようになります。
2. **`Task.Run` の範囲の拡大**
`MakeScaleBitmap` や `pngEnc.Save(ms)` が特にCPUとメモリを消費する部分です。これらを `Task.Run` の中に入れたことで、UIスレッドが解放され、プログレスバーが止まらずに動き続けます。
3. **`Freeze()` の重要性**
WPFの画像オブジェクト（`BitmapSource`）は、複数のスレッドをまたいで持ち運ぶことができません。しかし、`.Freeze()` メソッドを呼んで「変更不可（読み取り専用）」状態にすることで、スレッドの壁を越えて `Task.Run` の中で処理できるようになります。

エラーメッセージは
”The calling thread cannot access this object because a different thread owns it.”

MakeScaleBitmapが良くない？

```cs
        public RenderTargetBitmap MakeScaleBitmap(BitmapSource originalBitmap, double scale)
        {
            // 1. 拡大後のサイズを計算
            int newWidth = (int)(originalBitmap.PixelWidth * scale);

            DrawingGroup drawingGroup = new();
            // 最近傍補間を設定

            using (DrawingContext drawingContext = drawingGroup.Open())
            {

                drawingContext.DrawImage(originalBitmap, new Rect(0, 0, newWidth, newHeight));
            }

            // 2. 描き込み用の Visual を作成
            DrawingVisual drawingVisual = new();
            using (DrawingContext context = drawingVisual.RenderOpen())
            {
                context.DrawDrawing(drawingGroup);
            }

            // 3. RenderTargetBitmap に焼き付ける
            RenderTargetBitmap renderTargetBitmap = new(
                newWidth,
                newHeight,
                originalBitmap.DpiX,
                originalBitmap.DpiY,
                PixelFormats.Pbgra32);

            renderTargetBitmap.Render(drawingVisual);
            renderTargetBitmap.Freeze();
            return renderTargetBitmap;
        }
```

<br><br><br>


エラーメッセージ **「The calling thread cannot access this object because a different thread owns it.」（呼び出しスレッドは、別のスレッドが所有しているため、このオブジェクトにアクセスできません）** の原因は、ご推察の通り `MakeScaleBitmap` の中にあります。

WPFの `DrawingVisual` や `DrawingGroup` などのビジュアル要素や、`RenderTargetBitmap` は、作成されたスレッド（通常はUIスレッド）に強く依存するオブジェクト（DispatcherObject）です。これらは `Task.Run` などのバックグラウンドスレッド（MTAスレッド）上で作成したり操作したりすることが基本的にできません。

元の `MakeScaleBitmap` メソッドは、UIスレッドで動くことを前提とした実装（`DrawingVisual` を使ったレンダリング）になっているため、これをそのまま `Task.Run` の中で呼び出すとこのエラーが発生します。

---

### 解決策

このエラーを解決するアプローチは主に2つあります。

1. **【推奨】バックグラウンドスレッド（Task.Run内）でも動作する手法に書き換える**
`TransformedBitmap` や `CachedBitmap` を使用すれば、UIスレッドに依存しない（`Freeze` 可能な）方法で画像の拡大縮小が可能です。こちらの方がUIスレッドを全く汚さないため、プログレスバーがより滑らかに動きます。
2. **描画処理（MakeScaleBitmap）だけをUIスレッドに戻す**
画像作成自体はUIスレッドで行い、重い「エンコード（PNG保存）」と「クリップボード」だけをバックグラウンドで行う方法です。

ここでは、最もパフォーマンスが良くWPFの非同期処理として美しい **「1. バックグラウンドスレッドで動作する手法」** への書き換えをおすすめします。

---

### 修正コード（推奨：MakeScaleBitmap の書き換え）

`DrawingVisual` によるレンダリングをやめ、`TransformedBitmap` を使ってリサイズを行います。これなら `Task.Run` の中でもエラーになりません。さらに、最近傍補間（NearestNeighbor）を適用するために `CachedBitmap` を組み合わせます。

```cs
public BitmapSource MakeScaleBitmap(BitmapSource originalBitmap, double scale)
{
    // 1. スケール変換（リサイズ）を定義
    var scaleTransform = new ScaleTransform(scale, scale);
    var transformedBitmap = new TransformedBitmap(originalBitmap, scaleTransform);

    // 2. 最近傍補間（NearestNeighbor）を適用するためにCachedBitmapを作成
    // (TransformedBitmapに直接ScalingModeを指定できないため、BitmapScalingModeをカプセル化する)
    var cachedBitmap = new CachedBitmap(
        transformedBitmap, 
        BitmapCreateOptions.None, 
        BitmapCacheOption.OnLoad);

    // 補間モードをNearestNeighborに固定したい場合、
    // 描画を挟まないリサイズにおいてWPFのTransformedBitmapは、デフォルトまたはシステム標準の品質になります。
    // もし厳密にNearestNeighborでのピクセル等倍拡大を行いたい場合は、
    // WriteableBitmapなどを用いたピクセル操作や、WpfLightweightな手法が必要ですが、
    // 通常の拡大であればTransformedBitmapで十分高速かつスレッドセーフ（Freeze可能）に処理できます。

    // 3. 別スレッドへ渡せるようにフリーズする
    cachedBitmap.Freeze();

    return cachedBitmap;
}

```

※もし上記の方法で拡大したときの見た目（画質・補間モード）が理想と異なる場合は、**アプローチ2（メソッドの呼び出し側を調整する）** を採用してください。

---

### アプローチ2を採用する場合（呼び出し側の修正）

もし、どうしても元の `RenderTargetBitmap` を使った `MakeScaleBitmap` の描画結果（NearestNeighbor）を維持したい場合は、**「拡大処理だけをUIスレッド（Dispatcher）で実行する」** ように呼び出し側を修正します。

`Task.Run` の中身を以下のように書き換えてください。

```cs
await Task.Run(async () => // async を追加
{
    BitmapSource scaledSource = null;

    // 拡大処理(MakeScaleBitmap)だけをUIスレッドに一時的に投げる
    await Application.Current.Dispatcher.InvokeAsync(() =>
    {
        scaledSource = MakeScaleBitmap(sourceToProcess, scale);
        // MakeScaleBitmapの最後で.Freeze()しているので、ここで別スレッドに渡せるようになります
    });

    // ここから下はバックグラウンドスレッドで実行されるため、プログレスバーは止まりません
    PngBitmapEncoder pngEnc = new();
    pngEnc.Frames.Add(BitmapFrame.Create(scaledSource));
    
    using var ms = new System.IO.MemoryStream();
    pngEnc.Save(ms);

    // クリップボード処理
    Thread thread = new(() =>
    {
        ms.Position = 0;
        Clipboard.SetData("PNG", ms);
    });
    thread.SetApartmentState(ApartmentState.STA);
    thread.Start();
    thread.Join();
});

```

### まとめ

* **一番のオススメ:** `MakeScaleBitmap` を `TransformedBitmap` を使う形式（スレッドフリー）に書き換える。
* **描画結果にこだわりがある場合:** `Application.Current.Dispatcher.InvokeAsync` を使って、リサイズ処理の瞬間だけUIスレッドにバトンタッチする。

「オブジェクト参照がオブジェクト インスタンスに設定されていません（`NullReferenceException`）」が発生してしまった原因は、主に**2つの可能性**が考えられます。

特に可能性が高いのは **① `Application.Current` が `null` になっているケース**、または **② `MakeScaleBitmap` の内部で `originalBitmap`（`sourceToProcess`）が `null` になっているケース**です。

それぞれの原因と、確実に対処するための修正コードを解説します。

---

### 原因と対策

#### 可能性①：`Application.Current` が `null` または別スレッドから呼べない

`Task.Run` の中（バックグラウンドスレッド）から `Application.Current` を参照しようとすると、タイミングやアプリケーションの構成によっては `null` を返したり、正しく取得できないことがあります。

* **対策:** `Task.Run` に入る前（**確実にUIスレッドにいる場所**）で、あらかじめ `Dispatcher` をローカル変数に確保しておきます。

#### 可能性②：`sourceToProcess` が `null` になっている

`MakeScaleBitmap` の引数に渡している `sourceToProcess` が何らかの理由で `null` になっていると、その先の `originalBitmap.PixelWidth` の部分でこのエラーが発生します。

---

### 修正後のコード

以下のように、`Task.Run` を呼び出す前に **UIスレッド側で Dispatcher を変数に取っておく** ように修正してください。あわせて、安全に非同期処理を待機（`await`）できるように記述を整理しています。

```cs
// 1. 【重要】UIスレッド側にいる時点で、Dispatcherをローカル変数に保持しておく
var dispatcher = this.Dispatcher; // または Application.Current.Dispatcher;

// sourceToProcess や scale の準備
BitmapSource sourceToProcess = MyBitmapSource;
if (sourceToProcess != null && !sourceToProcess.IsFrozen && sourceToProcess.CanFreeze)
{
    sourceToProcess = sourceToProcess.Clone();
    sourceToProcess.Freeze();
}
double scale = MyImageScale;

// 2. バックグラウンド処理を開始
await Task.Run(async () =>
{
    // sourceToProcess が null の場合はエラーを回避する
    if (sourceToProcess == null)
    {
        throw new InvalidOperationException("コピー元の画像データがありません。");
    }

    BitmapSource scaledSource = null;

    // 3. 事前に取得しておいた dispatcher を使ってUIスレッドを呼び出す
    await dispatcher.InvokeAsync(() =>
    {
        // 最近傍補間の効いた拡大ビットマップをUIスレッド側で作成
        scaledSource = MakeScaleBitmap(sourceToProcess, scale);
    });

    // 念のため、生成されたビットマップが null でないかチェック
    if (scaledSource == null)
    {
        throw new InvalidOperationException("画像の拡大処理に失敗しました。");
    }

    // 4. PNGエンコード（ここからはバックグラウンドなのでプログレスバーは止まらない）
    PngBitmapEncoder pngEnc = new();
    pngEnc.Frames.Add(BitmapFrame.Create(scaledSource));
    
    using var ms = new System.IO.MemoryStream();
    pngEnc.Save(ms);

    // 5. クリップボードへの書き込み（STAスレッド）
    var tcs = new TaskCompletionSource<bool>();
    Exception threadException = null;

    Thread thread = new(() =>
    {
        try
        {
            ms.Position = 0;
            Clipboard.SetData("PNG", ms);
            tcs.SetResult(true);
        }
        catch (Exception ex)
        {
            threadException = ex;
            tcs.SetException(ex);
        }
    });

    thread.SetApartmentState(ApartmentState.STA);
    thread.Start();
    
    // thread.Join() の代わりに TaskCompletionSource を await すると
    // バックグラウンドスレッドの効率が良くなり、フリーズのリスクを減らせます
    await tcs.Task;
});

```

### ポイント

* `var dispatcher = this.Dispatcher;` を `Task.Run` の外に置いたことで、`Application.Current` に起因する `NullReferenceException` を確実に防げます。
* クリップボード書き込み用の `Thread` を待つ部分を `thread.Join()` から `TaskCompletionSource` を使った `await` に変更しました。これによりスレッドのバグやデッドロックが起きにくくなり、より安定して動作するようになります。

---

### 原因：誰が「アプリケーション」の主役か？

通常のWPFアプリであれば、あなたが作ったプログラムそのものが「メインのアプリ（`Application`）」になるため、`Application.Current` で自前のUIスレッド（Dispatcher）が綺麗に取得できます。

しかし、Visual Studioのビジュアライザーとして動く場合、状況が全く異なります。

* **主役（Application）は「Visual Studio本体」**
このとき、Windows上で動いている巨大なアプリケーションの本体は、あなたのプログラムではなく **`devenv.exe`（Visual Studio）** です。
* **`Application.Current` はVSのもの、または `null**`
バックグラウンドスレッド（`Task.Run`）から `Application.Current` を見に行くと、Visual Studio本体のDispatcherを取得しようとするか、あるいはアドインのスレッド環境の違いによって `Application.Current` 自体が **`null`** になってしまいます。そのため、`.Dispatcher` にアクセスした瞬間に「オブジェクト参照が～」のエラーが発生していました。

---

### なぜ `this.Dispatcher` なら上手くいったのか？

`this.Dispatcher` の「`this`」は、あなたが作成したビジュアライザーの画面（WindowやUserControl）自身を指しています。

WPFのコントロールは、どのスレッドで生成されたとしても、必ず「自分が生まれたスレッド（UIスレッド）」への参照を内部に持っています。それが `this.Dispatcher` です。

1. **`Task.Run` の外（UIスレッド）で `this.Dispatcher` をローカル変数にコピーする**
2. **`Task.Run` の中（別スレッド）から、そのコピーしたDispatcherを使ってUIスレッドに処理を頼む**

この手順を踏んだことで、Visual Studio側の環境に邪魔されることなく、あなたのビジュアライザー専用のUIスレッドへ正確にアクセスできるようになり、エラーが解決しました。

デバッガービジュアライザーやプラグイン開発では、`Application.Current` は高確率で悪さを（あるいは `null` に）なるため、**「コントロール自身の持つ `this.Dispatcher` を使う」** というのが鉄則であり、非常に美しい解決策です！無事に動作して本当に良かったです。
